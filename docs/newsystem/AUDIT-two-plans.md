# 两份方案对比审计（ChatGPT v2 vs 豆包全案）

> 审计对象：
> A = `Leyova-方案v2-运营OS（重心重排）.md`（ChatGPT，505 行）
> B = `Leyova_AI_Native_总体架构与实施全案_2026-11-16.docx`（豆包，28 节 / 约 5 万字）
> 审计基准：你的约束——**客户是中小企业**、**AI+运营不是 ERP**、**直播+跨境双焦点**、**模块化可开关可收费**、**亿元营收/千万级数据**。
> 方法：逐节阅读 + 关键事实外部核验（PostgreSQL 版本、开源许可证）+ 与现有施工单对照。

---

## 0. 结论先行

1. **两份都不是"AI 套壳"，水平都高于市面常见方案**；但取向相反：A 是**产品派**（先把运营的一天跑通），B 是**架构派**（先把企业级地基画全）。
2. 在你的约束下：**A 适合做产品骨架，B 适合做架构标尺。** 单选取 A；但 A 缺多租户与商业化，直接照做**做不成 SME SaaS**。
3. 加权得分（权重按 SME 场景）：**A 7.75 / B 7.03**（详见 §2）。
4. 两份**都缺** SME 的关键三件：30 分钟自助开通、按店铺+模块的低价套餐、每租户 AI 成本上限。这三件不是体验问题，是商业模型能否成立的问题。

## 4. A（ChatGPT）的最强三点与致命三点

### 最强三点

1. **对象模型换主轴：`Session` 是唯一一等公民**（§2）。货/流量/人/场是四个可调变量，商品库与订单退回"输入/输出"。这一刀切中了旧系统"商品/订单当主角"的病根。
2. **把系统写成"运营的一天"**（§3 日循环 + §6 三十个 Action + §7 四个工作面）。这是"功能清单"与"操作系统"的分水岭：一天只打开 4 次、每次 <10 分钟，是可验收的产品承诺。
3. **用"延后 + 触发条件"反 ERP**（§5.2、§9、§13.7）。12 张表起步、结算只留 3 个口径、拆分要等指标——每一条都写清"到什么数才做"，这是防臃肿最有效的方式。

### 致命三点

1. **没有多租户**。全文只在 §12.4/§13.2 提了 `tenant_entitlement` 和 S3 档"多客户"，但没有 RLS、没有租户上下文、没有配额与隔离测试。**客户是 SME → 一定是多租户 SaaS → 这份方案的数据层要重做一层。**
2. **没有 SME 落地链路**：没有开通向导、没有 Excel 模板、没有定价套餐、没有移动端。O1 假设"用真实导出数据"，但没说客户 30 分钟内怎么把数据弄进来。
3. **跨境只当"运营节奏"，合规被忽略**（§8）。"上新速度、活动报名、履约时效"是对的，但 **GPSR/EPR/CPC 缺失会直接 block listing、甚至封店**；这不是财务问题，是上架前置闸门，方案里没有。

## 5. B（豆包）的最强三点与致命三点

### 最强三点

1. **`Decision Case` 统一决策对象**（§3.1）。字段包含 subject/evidence/diagnosis/proposal/approval_policy/execution_ref/outcome/versions——比 A 的 Action 更完整，和"可执行物 + 证据 + 审批 + 回放"的思路同构。
2. **架构边界与一致性写得很硬**（§5、§7、§9、§15、§20、§23）：领域依赖单向、跨域只走 API/事件、Outbox 至少一次+幂等、RLS 多租户、指标口径版本化、SLO 与 RPO/RTO。这是可以直接拿去做架构评审的底稿。
3. **模块化与商业化闭环**（§16、§18）：manifest + capability 冲突校验 + 三层开关（编译/部署/运行期）+ entitlement + metering + 停用与删除分离。比 A 更完整。

### 致命三点

1. **和 SME 客户错位**。首期技术栈 = Nuxt 4（SSR）+ Temporal + LangGraph + PG + 对象存储，路线里还列了 7 个团队角色（§26.1）。SME 供应商要么是 1–3 人，要么是把实施成本转嫁给客户——两条都走不通。
2. **路线顺序重蹈旧系统**：阶段 2「数据与指标」排在阶段 4「直播运营闭环」之前（§26）。这正是 A 在 §0 自证过的错误——**先做 3–6 个月数据工程，运营才第一次被服务**。
3. **不定价**。§18 明确写"计费示例（仅结构，不定价）"，而 SME 生意的生死线就是"月费 399 能不能覆盖成本"。没有定价与成本模型，商业化章节等于没落地。

## 6. 八处正面冲突：谁对

| # | 冲突 | A 的主张 | B 的主张 | 裁决 |
|---|---|---|---|---|
| 1 | 系统主轴 | 场（Session）为中心 | 商品主数据 + 五引擎 | **A 对**：直播运营的主语是"这一场"；但商品主数据仍是事实底座，二者不是二选一（场是运营对象，SKU 是事实主体） |
| 2 | 起步表数 | 12 张，其余延后 | 分层完整（Raw→Canonical→Fact→Semantic） | **A 对**：SME 首期不需要五层；保留 staging→canonical→fact 三层即可 |
| 3 | 长流程引擎 | pg-boss 先上，Temporal 后置 | Temporal 是唯一长流程引擎（首期） | **A 对**：Temporal 多两个容器与一套运维；SME 的流程是"短链路+人审+定时"，pg-boss + 状态机够 |
| 4 | Agent 编排 | Mastra vs LangGraph 做 A/B | LangGraph 唯一主框架 | **都不完全对**：状态必须在自己的库里（可 JOIN 权限与租户），框架只能当执行器；选型用一周 A/B 决定，不锁死 |
| 5 | 全栈框架 | 未指定（隐含 React 生态） | Nuxt 4 + Vue 3 + Nitro | **平手**：内部运营系统不需要 SSR；但 SaaS 官网/SEO 用 Nuxt 有价值。建议业务台 SPA、官网另起 |
| 6 | ClickHouse 时机 | S2（1–10 亿 GMV）引入 | 按多信号触发（数千万–上亿行、P95 不达标） | **B 更严谨**：触发条件写得比 A 细；两者结论一致 |
| 7 | 多租户 | 基本缺失 | RLS + 复合键 + API Scope + 攻击测试 | **B 对**，且是 A 的硬伤 |
| 8 | 商业化 | 只做 entitlement 闸门 | 套餐/计量/账单/License 全套 | **B 更完整，A 更务实**：SME 首期只需 entitlement + 计量，账单可后置；但定价模型必须有 |

## 7. 合并建议：A 做骨架，B 做标尺，SME 层两份都要补

### 7.1 直接采用 A 的部分（产品骨架）

- 场为中心的对象模型与"四个可调变量"
- 日/周/月三条运营循环；30 个 Action 清单；4 个工作面（不是 12 屏）
- "AI 默认执行、人管例外"+ L1–L4 动作分级（但 L3 以上必须审批）
- 12 张表起步 + 延后清单 + 触发条件
- 容量三档与拆分阈值；SLO 指标
- 6 个模块、4 个可单独卖；三个闸门（Action/metric/screen）
- O1 两周可演示的路线

### 7.2 直接采用 B 的部分（架构与治理）

- DDD 边界与依赖规则（跨域只走 API/事件，不读对方表）
- Outbox + 幂等 + 死信 + 重放
- 多租户 RLS + 复合键 + API Scope + 越权测试
- 指标口径版本化 + Evidence Packet（与 A 的证据要求合并）
- 模块 manifest + capability 冲突校验 + 停用/删除分离
- 风险分级 R0–R4、工具网关、执行回执
- SLO/DR/备份 RPO-RTO、许可证 SBOM 扫描
- PostgreSQL 版本基线（18.7）与 CH 进入机制

### 7.3 两份都缺、必须补的六件（SME 生死线）

1. **30 分钟自助开通**：3 步向导 + 6 套 Excel 模板 + 示例数据。
2. **Excel 为主路径**：没有 API 资质也能用；只传订单也能出降级复盘。
3. **按店铺 + 模块的低价套餐**：入门 399 / 专业 899 / 跨境 1299，试用 14 天，无实施费。
4. **每租户 AI 成本上限**：默认 ￥100/月，超限降级为"只取数不出结论"。
5. **移动端四页**：待办/提词卡/告警/复盘，375px 可用。
6. **跨境合规闸门**：GPSR/EPR/CPC 缺失即阻断上架（A 缺、B 只提"本地合规"未到字段级）。

## 8. 最终判断

| 问题 | 答案 |
|---|---|
| 哪份更好？ | 按你的约束：**A 更好用，B 更正确**。A 是能开工的产品方案，B 是能过评审的架构方案。 |
| 只能选一份做底稿？ | **选 A**，把 B 的 §5/§9/§15/§16/§18 作为架构附件并入。 |
| 照 A 直接做会怎样？ | 两周能演示，但一到"第二个客户"就会因为无多租户、无开通、无定价而返工。 |
| 照 B 直接做会怎样？ | 架构很稳，但 3 个月见不到运营价值，SME 客户与 1–3 人团队都撑不到那天。 |
| 最该警惕的信号 | A 的"AI 默认执行"与 B 的"Temporal 唯一编排"——前者会踩平台规则，后者会拖死 SME 交付。 |

**一句话：A 负责"让运营明天就用上"，B 负责"让系统三年不塌"；SME 生意要求两者同时成立，所以只能合并，不能二选一。**
